# 每开一个新对话怎么交接

> 一段对话 = 一个任务（任务清单「使用说明」的第一条）。
> 这份是通用方法与模板，具体某个任务的成品 prompt 见 `docs/交接_Txx.md`。

---

## 核心机制：让 `docs/进度.md` 当交接的载体

新对话里的 agent 没有任何记忆。它不知道上一轮改了什么、踩过什么坑、你和上一个 agent 定过什么规矩。

所以每轮只做两个动作，闭环就成立了：

1. **开头**：让它先读 `docs/进度.md`
2. **结尾**：要求它更新 `docs/进度.md`

只要这两步不断，`进度.md` 就会一直是「最新的项目状态说明书」，你不需要每次凭记忆复述上下文。**任何口头约定都要落进这个文件，否则下一轮就没了。**

---

## 每次要附的文件

**每次都附**（3 个）：

- `docs/进度.md` —— 进度、决策、已知坑
- `收敛版需求说明.md` —— 业务口径唯一来源
- `AI销售复盘助手_开发任务清单_v2.md` —— 验收标准原文

**按任务加**：

| 任务类型 | 加什么 |
|---|---|
| 碰逐字稿 / 指标 / 评分（T13、T14、T17~T24） | `frontend/src/types/types.ts`、`frontend/src/config/scoring.ts` |
| 碰数据库 / 种子（T15、T16） | `backend/src/db/schema.ts`、`backend/src/seed.ts` |
| 碰 AI 链路（T25~T28） | `backend/mock/difyResult.json`、`backend/src/dify.ts` |
| 碰页面（T29~T46） | 相关页面文件 + `frontend/src/api/client.ts` |

**不用附**：`node_modules/`、`backend/data/app.db`、跟本任务无关的页面代码。附多了它会分心去改不该改的地方。

## Prompt 模板

照这七段填，缺哪段就会在哪段出问题。

```
我在做一个「AI 销售复盘助手」的 MVP Demo。技术栈：后端 Node + Hono +
Drizzle + SQLite(better-sqlite3)，前端 React + Vite + Tailwind。
项目根目录已是 git 仓库。

先读 docs/进度.md，那里面有当前进度、已经定下的决策和已知的坑。
再读《收敛版需求说明》——全部业务口径以它为唯一来源，不许自己编。

### 本次只做一个任务：Txx <任务名>
任务原文与验收标准见《开发任务清单》Txx 一节。不要顺手做后面的任务，做完就停。

### 交付物
<明确到文件路径。含糊的话它会自己挑地方建文件>

### 硬性约束
<格式要求、不许改的文件、口径里最容易搞错的几条，逐条列>

### 目标结果
<能量化就量化。比如「总分 1 分」比「打得差」有用一百倍>

### 别的约束
- 不许改 <列出不该动的文件>
- 不要替我 git commit
- 如果发现我给的要求与《收敛版需求说明》冲突，先停下来告诉我，不要自己选一个

### 做完之后
1. 报告改了哪些文件
2. 按验收标准逐条自查，附验证命令与实际输出
3. 告诉我怎么自己验证
4. 更新 docs/进度.md：本任务状态、验收结果、总览表，新问题追加到「未决问题」
```

## 七条经验（都是这个项目上已经踩过的）

**① 「本次只做一个任务，做完就停」这句必须写。**
T12 那轮没写，结果它顺手把 T15 的客户和复盘数据也灌了，还带进来 14 处内部矛盾。多做的部分没人验收，等于埋雷。

**② 目标结果要量化。**
「打得差的逐字稿」它能给你一份看着很差、算出来 3 分的东西。「总分 1 分，D1 得 1 分其余为 0，销售说话占比 0.75~0.80」它就没得发挥。

**③ 「不许改 XX」要点名到文件。**
说「别乱改」没用。列出文件名它才会绕开。

**④ 冲突要它停下来问，不要它自己选。**
需求文档和你的口头描述打架时，它默认会挑一个往下做，还不告诉你。这一条写进 prompt 能省掉整轮返工。

**⑤ 一个对话装不下的任务，开工前就拆，不要边做边拆。**
T15 要写六条 30 分钟的逐字稿，一轮做不完。拆成 a / b / c / d 四轮之后每轮都干净收尾了。
拆的标准不是「工作量四等分」，而是**每一份都能单独验收**：
T15-a 是骨架加自检脚本，b / c / d 各扩写两条复盘，每轮结束都能跑一遍脚本看退出码。
拆的时候把「这一份的验收标准」也一并写进交接文档，否则下一轮 agent 不知道自己算不算做完了。

**⑥ 自检脚本全绿 ≠ 做对了，尤其当那个脚本也是 AI 写的。**
这是最贵的一条。`verifySeedReviews.mjs --strict` 47 项全过，
但 R3 的「开放式提问数」存了 5、实际一句都不成立，从交付一路活到人工复核才被抓出来。
原因是这个指标要理解语义才能数，脚本数不了，就直接采信了数据里的存值，
而算分的那一节又拿这个存值去反推分数——**自己给自己判卷，怎么跑都是绿的**。

所以：**先问「这个脚本验不了什么」，再看它的绿色**。
好在这个项目里两个脚本都主动把自己的盲区印出来了（`verifyTranscript.mjs` 第九节、`进度.md` 的 P5），
让 agent 写自检脚本时就要求它加这一节。盲区清单里的每一项，都得有人拿眼睛看过。

**⑦ 交接文档用完就删。**
`docs/交接_Txx.md` 只在那个任务进行期间有效，任务验收通过后立刻删掉。
留着的话，下一轮 agent 会读到一份描述着「待完成」的过期文档，然后照着它去重做已经做完的事。
`docs/进度.md` 是唯一一份长期文件，所有需要跨轮存活的信息都要落在它里面，不能只写在交接文档里。

## 复核：脚本跑完之后，人要查的是什么

一个任务交付、脚本全绿之后，值得再花一轮做人工复核。别重跑一遍脚本——那没有新信息。
**要查的恰恰是脚本声明自己查不了的那些东西。**这一轮实际用的四个角度，可以照搬：

1. **公式类**：凡是「由某个规则算出来」的数，全部重算一遍。
   这次是逐字稿每条的时长（字符数 ÷ 3.05 + 0.6），659 条逐条重算，确认没有一个是手编的。
2. **计数类**：凡是「数出来」的数，重新数一遍。打断次数、问句数、卖点命中数都属于这类。
3. **口径类**：把判定口径的原文找出来，逐条套。R3 那个错就是这么查出来的——
   口径写在 `backend/mock/README.md`（开放式 = 无法用「是/否/一个数字」作答），
   把九句问句摊开一句句套，一句都不成立。**口径原文往往不在你正在改的那个文件里，要专门去找。**
4. **副本一致性**：同一组数值被抄在几处（代码注释、`进度.md`、脚本的期望值），
   挑几个辨识度高的数值确认几处都对得上。见 `进度.md` 的 P7。

做法上有两点值得固定下来：

- **写一次性脚本，跑完即删。**命名成 `scripts/_xxx.mjs` 之类，不入库、不被任何地方引用，
  复核完连同临时文件一起删掉。目的是让复核过程可重放，而不是靠肉眼扫几百行。
- **查出问题时，优先改内容而不是改数字。**
  R3 那处，把存值从 5 改成 0 也能让数据自洽，但那是掩盖：R3 在设计上就是「需求挖掘强」的那一侧，
  写成封闭式问句本身才是笔误。所以改的是那五句台词，不是那个数字。
  **判断标准：如果改完之后，这份数据想演示的那件事就演示不出来了，那你改错了地方。**

## 你自己要做的两件事

**验收不能交给 AI。**任务清单原文就写了这条——它倾向于告诉你「符合预期」。每轮结束你自己按验收标准跑一遍命令、看一眼输出。

要它贴**实际输出**，不要它贴结论。「已验证通过」这四个字没有任何信息量；
退出码要一条条单独取，不要写在管道后面（`a | tail` 取到的是 `tail` 的退出码，永远是 0）。
再要它做一次**负向测试**：故意改坏一处，确认脚本真的报错、退出码真的变成 1，然后还原。
脚本抓不到人为注入的错，说明它对真错误也是瞎的。

**过了就 commit。**message 写成 `T13 完成：逐字稿样本 A`。下一轮出问题时能干净地退回来。
