## 三、已有能力、架构边界与已知冲突

- 14 项指标计算、阈值判定与四维评分已完成。页面必须调用现有 `buildReviewAnalysis()`，不得在组件里另写一套评分。
- 所有评分阈值统一来自 `frontend/src/config/scoring.ts`。T37 页面显示门槛时也必须读取配置，不得复制字面量。
- 样例 A / B、语义证据锚点和装修产品 seed 已固定。不得为了页面好看修改样本、阈值、评分函数、mock 或产品数据。
- `AiResult` 已有完整兜底，数组字段为空时页面负责显示“本次未检出”，不得把空数组当异常。
- 客户状态 S1/S2/S3 不落库：按客户 `reviews` 数量实时派生，0 条为 S1、1 条为 S2、2 条及以上为 S3。
- `intent_manual` 是人工覆盖保护开关；为真时，后续自动判定只能记录系统建议，不能覆盖实际 `intent_level / intent_score`。
- 作战包不建表，T41 才开始实现。本阶段禁止创建 battlecard 表、接口或页面。

### 3.2 页面与响应式边界

- 同一套 React 页面同时服务手机和网页端：
  - 窄屏：底部四 Tab“待办 / 新建 / 复盘 / 我的”；
  - 宽屏：左侧导航 + 内容区，不是把手机布局简单横向拉伸。
- T29-T40 不得提前增加“作战包”一级入口；作战包属于后续任务，通过客户上下文进入。
- 当前项目未安装路由库。T29 可使用浏览器 History API 实现小型路由，或在确有必要时新增轻量路由依赖；无论采用哪种方式，都必须满足地址栏同步和刷新保留页面。
- 每个页面必须有可访问的标题、按钮文本、表单标签和键盘焦点；不要只靠颜色表达状态。

### 3.3 T31/T32 的种子数据冲突——不得静默处理

任务清单旧验收写的是：

- T31 客户库看到 3 个客户；
- T32 打开某个 S1 客户，8 项档案中 5 项“待确认”。

但当前已经过 T15/T16 验收的真实 seed 是 7 个装修客户：

- 2 个 S3、2 个 S2、3 个 S1；
- 三个 S1 客户当前均只有“称呼与身份、核心需求”两项有值，即 8 项中 6 项待确认。

因此到 T31 前必须向用户明确说明冲突并确认口径：

1. 页面展示当前全部 7 个 seed 客户；或
2. 定义不破坏 seed 的明确筛选规则，只展示 3 个 demo 客户。

禁止为了满足旧文字直接删除 4 个客户、篡改 seed、伪造第五个已填字段或在 UI 中隐藏无依据的数据。用户未确认前，T31 不得标记完成。

### 3.4 数据写入与测试隔离

- 页面开发与自动化测试一律 `USE_MOCK=true`，真实 Dify 调用数为 0。
- 会修改数据库的验收优先使用临时 SQLite 文件；若必须使用 `backend/data/app.db`，测试结束后运行 `npm run db:seed` 恢复固定初始状态。
- 不得提交 `.env`、SQLite 数据库、前端 `dist` 或测试产生的临时文件。
- T40 的 reviews + needs + todos 属于一次业务提交，不能靠三个互不关联、可能半途失败的前端请求冒充原子落库。应新增专用后端接口并使用数据库事务，且注册在通用 CRUD 之前。
