# UI 与交互优化任务清单

## UX01：界面减字与动作层级统一

### 目标

减少移动端首屏的可见文字和重复说明，让用户先看到“现在是什么状态、下一步能做什么”。

### 范围

- 审查 App.tsx、PageStates.tsx 和 12 个页面的标题区、按钮、状态说明、空状态。
- 缩短重复或过长的按钮文案；同一动作统一用词。
- 主界面只保留当前决策需要的信息，次要背景用“说明”折叠区、帮助提示或字段辅助文字渐进披露。
- 返回动作、主要动作、次要动作建立一致的视觉层级。
- 图标化只用于含义明确的动作，并补齐 aria-label 和可见焦点。

### 禁止

- 不得删除 Mock 模式、安全警告、错误原因、待确认状态或业务必要信息。
- 不得把所有按钮都改成只有图标。
- 不得改变路由、API、业务口径或数据。

### 验收

- 390×844 下四个一级页面首屏都能清楚看到主标题与主要动作。
- 不出现“按钮旁边又有一段重复解释按钮功能”的情况。
- 1440×900 下页面不过度空洞，层级仍清楚。
- 键盘、读屏名称和焦点状态不退化。
- npm run lint 与 npm run build 通过，浏览器控制台无新增错误。

## UX02：列表搜索、筛选与快速定位

### 目标

让用户不用长滚动就能找到客户、话术、产品和报告。

### 范围

- 客户库增加搜索框、清空按钮、结果数量和无结果状态。
- 客户搜索至少覆盖姓名、身份、联系方式、行业、核心需求中当前已加载的数据。
- 客户库提供阶段或意向快捷筛选；搜索与筛选可以组合，清空后恢复完整列表。
- 话术库至少按内容、场景、行业查找。
- 产品库至少按名称、行业、参数和卖点查找。
- 团队报告在数据量较多时可按客户名或报告信息查找。
- 长列表提供“回到搜索”或“回到顶部”的快捷入口，不能遮挡原生底部安全区。

### 实现原则

- 当前数据量使用前端派生筛选，不擅自新增后端搜索协议。
- 搜索不修改原数组，不改变原排序规则。
- 输入框提供具体 placeholder，例如“搜索姓名、需求或电话”。
- 支持键盘操作；清空按钮必须有可访问名称。

### 验收

- 输入存在的客户姓名，只显示匹配项且结果数量正确。
- 输入身份、需求或电话片段也能找到对应客户。
- 组合筛选结果正确；清空后完整列表与原顺序恢复。
- 无结果时告诉用户当前条件，并提供一键清空。
- 话术、产品、团队报告搜索均覆盖规定字段。
- 390×844 与 1440×900 均无横向滚动。

## UX03：长档案的页内导航与快速跳转

### 目标

让用户在客户档案、作战包和复盘报告中快速跳到目标区块，并随时回到顶部或前一上下文。

### 范围

- CustomerDetailPage：为 8 项档案和“人工意向”增加页内目录。
- BattlecardPage：为客户信息、本次目标、产品或话术、风险或行动等实际区块增加跳转。
- ReviewResultPage：保留已有指标到逐字稿证据定位和窄屏“返回当前指标”，再增加报告级章节跳转，不能破坏现有逻辑。
- 对确实很长且有明确章节的其他页面按同一模式补齐。
- 移动端优先使用紧凑的原生 select 或可折叠目录；宽屏可使用 sticky 章节导航。
- 每个目标有稳定 id 和合适的 scroll-margin-top，跳转后焦点或当前状态清楚。
- 提供不遮挡底部 Tab 和安全区的“回到顶部”。

### 禁止

- 不得为了导航复制一份页面内容。
- 不得用窗口全局滚动替代 ReviewResultPage 已有逐字稿独立滚动。
- 不得破坏稳定报告 URL、指标证据锚点或高亮逻辑。

### 验收

- 客户档案从顶部可一键跳到第 8 项，再跳到人工意向，并能回顶部。
- 作战包每个主要区块均可准确定位。
- 报告的章节跳转、指标证据跳转和“返回当前指标”可以同时工作。
- 390×844 下目录不挤占首屏，1440×900 下 sticky 不遮内容。
- URL 刷新后页面仍能加载，控制台无错误。

### 建议 commit

## UX04：日期与时间选择体验

### 目标

取消要求用户手写日期时间的主要流程，新建时默认当天并提供快捷选择。

### 范围

- VisitCreatePage 的普通文本时间输入改为原生 datetime-local 或等价的可访问选择器。
- 新建拜访默认本地当天，时间采用合理的未来整点，不能默认成已经过去的时间。
- 提供“今天”“明天”“下周”等明确快捷项；点击后立即更新选择器和预览。
- 提交前以中文可读格式展示最终拜访时间。
- TodoPage 的截止日继续使用原生日期选择；已有日期原样显示，空日期在用户准备设置时默认今天。
- 提供今天、明天、下周快捷选择和清除截止日动作。
- 正确处理本地时区，保存到 ISO 后重新读取不能出现日期前后偏移。

### 业务边界

- 不得静默把数据库里 dueDate=null 的待办批量改成今天。
- 客户档案的“客户原话时间点”允许自然语言，不改成强制日期控件。
- 编辑已有数据时保留原值，不能每次进入页面都覆盖为今天。

### 验收

- 新建拜访打开页面就有当天有效默认值，无需键盘输入。
- 点击“明天”后日期准确变化，提交预览与保存后的时间一致。
- 空截止日准备设置时默认今天；取消或未保存不会修改后端。
- 已有截止日刷新后不被今天覆盖；清除后恢复“未设截止日”。
- iPhone 模拟器中点击字段出现系统日期和时间选择界面。
- 本地时区跨午夜边界的单元或纯函数测试通过。

## UX05：操作前预期、操作中反馈、操作后撤销

### 目标

建立一致、真实、可访问的操作闭环。

### 范围

先列出所有写操作，再按风险处理：

- 待办完成或恢复、截止日修改或清除；
- 创建拜访；
- 客户档案保存；
- 人工意向调整；
- 复盘报告保存；
- 亮点存入话术库；
- 配置页保存 API Key；
- 其他实际写操作。

统一要求：

1. 操作前：按钮名称说明结果；高风险或不可逆操作展示摘要并确认。
2. 操作中：按钮禁用、防重复提交、展示进度或正在处理的对象。
3. 操作成功：明确告诉用户改了什么，并给出下一步。
4. 操作失败：说明没有改动什么、如何重试，不能只写“失败”。
5. 可逆操作：出现限时撤销入口；撤销必须调用后端并刷新为真实数据。
6. 撤销失败：保持当前真实状态并明确提示，不能假装成功。

建议新增少量共享组件或 hook，例如统一状态提示、确认对话框、撤销条；避免每个页面复制不同实现。

### 特殊规则

- 人工意向撤销必须新增反向审计记录，不能删除历史日志。
- API Key 不能读取旧值，因此不能假装可以撤销；保存前必须明确二次确认。
- 复盘报告涉及多表原子写入。没有完整回滚 API 时，先做明确预览和不可逆确认，不要擅自直接删除多表数据。
- 创建拜访若新增撤销，必须确保关联 visit 或 todo 的数据完整性；做不到时先确认而不是做假撤销。
- 如果为了真实撤销必须增加最小 API，可以修改现有路由和 client，但不允许改 schema 或扩大业务范围。

### 验收

- 待办勾选成功后可以撤销，刷新后数据库状态与画面一致。
- 截止日修改后可撤销为原日期或 null。
- 客户档案保存后可撤销到提交前快照，刷新仍正确。
- 人工意向撤销后审计历史保留并新增反向记录。
- 快速双击提交只产生一次写入。
- 网络失败时按钮恢复可用、错误清楚、没有错误的成功提示。
- 确认对话框可用键盘操作，关闭后焦点正确恢复。

### 建议 commit

UX05 完成：统一操作反馈与撤销
