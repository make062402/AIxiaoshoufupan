## 3. 当前已确认的具体问题

### 3.1 文字密度

- 多个页面同时展示眉题、标题、解释段落、状态标签和长按钮文案，移动端首屏操作入口被向下挤。
- “返回”“查看”“保存”等动作有的用按钮、有的用文字链接，视觉层级不统一。
- 减字不能简单删内容。主界面保留结论和动作，次要说明放进“说明”折叠区、帮助提示或字段辅助文字。

### 3.2 查找与跳转

- CustomerListPage 当前无搜索和筛选。
- ScriptLibraryPage、ProductLibraryPage、TeamReportPage 随数据增加会变得难找。
- CustomerDetailPage 有 8 个连续档案区块和人工意向区，移动端滚动很长。
- BattlecardPage、ReviewResultPage 都是多区块长文档，需要保持已有证据定位能力并补齐页面级快速跳转。

### 3.3 日期输入

- VisitCreatePage 的“拜访时间”目前是普通文本框，依赖用户输入类似 2026-09-26 15:00。
- TodoPage 已使用 type=date，但空截止日不会默认展示当天，也没有今天/明天等快捷选择。
- 客户档案第 8 项是“客户原话时间点”，可能是“10 月中旬”“月底前”等自然语言，不得错误改成强制日期选择器。
- 空待办没有明确截止日是合法数据。只能在用户主动设置时默认今天，不能静默把数据库中的 null 批量改成今天。

### 3.4 操作反馈与撤销

现有不少按钮已有“保存中/创建中”，但缺少统一闭环：

- 待办完成与截止日修改：适合保存成功后提供真正的撤销。
- 客户档案保存：应保留提交前快照，成功后可恢复旧值。
- 人工意向调整：撤销应再写一条反向调整记录，不能删除审计历史。
- 创建拜访：应在提交前显示客户、场景、时间摘要；若实现撤销，必须真实删除或取消对应本地记录。
- 保存复盘报告：涉及多表原子写入，未经完整回滚设计不能轻率增加删除；至少在保存前显示明确摘要与不可逆提醒。
- 保存 Dify API Key：出于安全原因不能把旧 Key 返回前端，因此不能做假的撤销；必须在提交前明确确认影响。

## 4. 数据和安全边界

- 客户阶段只由复盘次数派生，不能向 customers 表新增阶段字段。
- Seed 后自增 ID 会变化，测试必须按姓名或业务条件查找，不能硬编码 ID。
- 本轮不修改数据库 schema、评分规则、Dify 输出契约、生产部署配置。
- 本地测试如果写固定数据库，结束后必须先取得用户对重置目标的确认；优先使用临时数据库。
- 真实 Dify 调用必须为 0。
- API Key 只能留在后端，前端永远不能读取旧 Key 原文。
