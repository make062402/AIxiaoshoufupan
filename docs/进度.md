**P5 的危害在 T15-d 上真实兑现了一次**（2026-08-23 人工复核查出，已修，详见本文件顶部「本轮复核」）：
R3 的 `open_question_count` 存 5，实际九句销售问句里**一句开放式都没有**，全是「是不是 / A 还是 B / 有几家」。

### P6 参数错误判定要限定「只对照产品库 params」

需求说明 §3.3 的口径是「讲错**或含糊带过**的参数条数」，「含糊带过」没有客观边界。样本 A 为了保证 `param_error_count` 恰好等于 1，已经把所有可能被读成「第二处含糊」的表述都改干净了（例如销售被追问检测报告时直接回避，而不是含糊地说「E0 就是最高标准」）。

**T27 写 Dify 提示词时要明确限定：只拿销售说出口的数字/年限/品牌/范围去和产品库 `params` 逐条对照，对不上才计数；销售没提到的参数不算「含糊带过」。**否则同一份样本 A 每次跑出来的 `param_error_count` 都不一样，T24 没法复现。

### P7 同一组数值手抄在三处，只有整体漂移能被自动抓到

样本 A 那 14 项指标的数值，现在同时存在于：

1. `frontend/src/samples/transcriptA.ts` 的头注释（给 T24 对照用）
2. `docs/进度.md` 本文件的 T13 一节（给下一轮 agent 看）
3. `scripts/verifyTranscript.mjs` 的 `SAMPLES.A.claim`（给脚本比对用）

其中第 3 处是**唯一会被机器验证的**——脚本拿它跟从逐字稿实算的结果比，对不上就 FAIL。第 1、2 处是纯文档副本。

脚本第八节做了缓解：挑十个辨识度高的数值（1761.2 / 1300.4 / 364.4 / 0.781 / 79.5 / 272.5 / 90.6 / 735.5 / 1365 / 2.04），要求它们在头注释和 `进度.md` 的 T13 节里都出现。

**但这是存在性检查，不是逐处一致性检查，实测确认了盲区**：同一个数值在文档一节里常出现多次（`0.781` 就同时在「四个特征」表和「14 项指标」表里），把其中一处改错、另一处没动，第八节仍会 PASS。它只能抓住「整体改掉 / 整段删掉 / 小节标题被改导致定位失败」。

**所以改动样本 A 或 B 的任何数值时，三处都要手动过一遍，不要指望脚本兜底。** 根治办法是让头注释和文档从 `claim` 生成，但那要引入构建步骤，对这个 MVP 不划算，暂不做。
