## 三、已有能力、架构边界与必须显式处理的冲突

### 3.1 作战包的数据边界

- T41 可新增专用 `GET /api/battlecard/:customerId`，且必须注册在通用 CRUD 前。
- T41 后端只负责一次性聚合原始数据：customer、实时 reviewCount/S 阶段、最新一条 review、该 review 的未满足 needs、同业产品、可用 scripts、相关 todos/visits。推荐排序和“必拿回三件事”属于 T42 前端纯函数，不要在接口和组件中各写一套。
- “上次复盘”必须按 `created_at DESC, id DESC` 确定唯一最新 review；未满足 needs 必须限定为该 review 的 `review_id` 且 `satisfied=false`，不能把客户全部历史未满足需求混在一起。
- S1 没有 review 时，latestReview 为 null、unsatisfiedNeeds 为空数组；这是正常数据，不是 404/500。
- 作战包不落库，不新增第 9 张表。T44 的“再做一次复盘后内容变化”必须来自重新读取数据库并现拼，而不是手工更新一份缓存作战包。

### 3.2 T42 的确定性组装规则

- 档案 8 项与缺口优先级必须复用需求说明 3.1 的业务口径；不要误用 D2 覆盖率的 `PROFILE_FIELDS` 顺序直接代替缺口优先级。
- 高优先级字段是 1、2、3、4、5、8；中优先级是 6、7。同优先级按字段编号升序。当前 S1 已填 1、2、5，因此必拿回三件事应为 3“在采购中的角色”、4“预算区间”、8“采购时间点/交付期限”。
- S1 产品从同一行业中按 `price ASC, id ASC` 取 2 个；不得跨行业，也不得把字符串价格按字典序排序。
- S2/S3 只用最新复盘的未满足需求。需求与产品卖点通过 `selling_points[].match_keywords` 匹配 need.text + need.quote；同一产品去重。
- S2/S3 排序：L1 对应产品优先于 L2；同级按需求被提及次数降序；再并列按产品 ID 升序。
- 需求匹配产品不足 2 个时，为满足“固定 2 个”，建议用 S1 低价规则补足并排除已选产品。这是从“固定 2 个 + 清单产品优先 + 清单空时回退”推导出的实现口径；若新对话中的用户不同意，必须先停下来确认，不能静默采用别的规则。
- 同一输入运行两次必须深度相等；不得使用当前时间、随机数、对象遍历偶然顺序或数据库默认顺序。

### 3.3 T43/T44 的页面与演示边界

- 作战包不是第五个一级入口；入口应从客户列表/详情或日程中的客户上下文进入。推荐稳定 URL：`/me/customers/:id/battlecard`。
- T43 的 S1 客户 `notes` 当前为空，因此 S1 页面应把注意事项显示为“待确认”，不能伪造忌讳。风险视觉样式可用 seed 中 notes 非空的 S2/S3 客户另行验收。
- T44 任务清单没有建立第二个 Dify 工作流的任务，当前仓库也只有“复盘分析”工作流。技术方案允许“五段式话术调用 Dify，或回落预置通用话术”；本阶段默认使用 scripts 表的五段式通用/个人话术，T41-T53 不得为了 T44 擅自真实调用 Dify或新增未经契约设计的工作流。
- 五段式阶段只能是：开场破冰 / 需求确认 / 方案呈现 / 异议处理 / 下一步锁定。每条展示 scene，异议处理话术应带开放式追问。
- T44 的闭环验收要选一个当前 S2 客户（如刘敏或郑帆），先记录作战包内容，再给同一客户完成一次复盘，返回相同作战包 URL 后确认 latest review、未满足需求/下次动作等内容变化。测试结束立即 reseed。

### 3.5 T46 API Key 配置冲突——必须先确认安全方案

- 任务清单写“配置页能填 API Key，保存后重启应用仍在”，但既有硬边界是 DIFY_API_KEY 只能存在后端，前端源码、响应、localStorage、IndexedDB、日志和截图中都不能出现原始 Key。
- 当前项目没有用户/管理员认证。如果在公开部署后直接暴露“修改服务器 Key”的无保护接口，任何访问者都能覆盖密钥；如果把 Key 存浏览器，又违反后端持钥边界。
- 到 T46 配置页时必须暂停并让用户选择安全范围。推荐方案是：
  1. 页面只显示“已配置/未配置”和掩码，不返回原始 Key；
  2. Key 仅提交到受保护的后端管理接口，原子写入被 Git 忽略的服务器环境文件，并更新当前进程；
  3. 管理接口至少需要独立的管理员口令/令牌或只允许本机访问；管理员凭据也不得进入前端持久存储或 Git。
- 如果用户不愿增加最小管理保护，则配置页只能做只读状态与修改说明，不能假装满足“可安全保存 Key”。该冲突解决前不得提交 T46，也不得开始 T47。

### 3.8 T50 的工具链与验收依赖冲突

- Android APK 需要 JDK、Android SDK/Gradle，并通常需要新增 Capacitor 依赖；先只读检测环境。缺失工具链或需联网安装时，应按权限规则请求用户批准，不得声称生成了 APK。
- Capacitor WebView 不能继续把 API 固定为相对 `/api`；应支持 `VITE_API_BASE_URL`，网页/PWA 默认同源 `/api`，Android 构建显式指向用户的 HTTPS 后端。不得把密钥写入 Vite 环境变量。
- iOS PWA 真机“添加到主屏幕”要求受信任 HTTPS，而 T52/T53 在 T50 之后。严格串行下，T50 最多能完成 manifest、图标、service worker、可安装性构建检查；真机验收要么使用用户已有的受信 HTTPS 测试地址，要么由用户明确同意在 T53 补做。未经确认不得把“构建通过”写成“iPhone 已安装通过”。
- APK、Gradle 缓存、签名文件、dist 等构建产物默认不进 Git；只提交源配置、图标、脚本和必要的锁文件。不得生成或提交生产签名私钥。

### 3.9 T51-T54 是外部环境任务，不能只靠本地结论

- T51-T53 需要用户提供/确认服务器 IP、SSH 用户与密钥方式、Ubuntu 版本、子域名、DNS 控制权和是否允许产生云资源费用。不要把 SSH 私钥、服务器密码、域名账号密码或证书私钥写进仓库、命令输出、文档或截图。
- 原任务清单注明 T51-T53 由用户在终端 SSH 操作。代理应优先在仓库生成可审查、可重复执行的 ops 脚本/配置模板和逐条命令，由用户授权后执行；涉及 sudo、DNS、证书签发、开放端口、PM2 自启动、服务器重启时须在动作前说明影响。
- T51 环境验证后，若云主机按量计费且暂不部署，应提醒用户停机；不要擅自删除实例。
- T52 必须以真实浏览器验证证书链、锁图标及 HTTP→HTTPS，不能只看 Certbot 输出。
- T53 要保证 SPA 路由刷新由 Nginx `try_files ... /index.html` 兜底，`/api/` 反代 Hono，SQLite 数据与 `.env` 位于持久位置，重新发布不能误覆盖生产数据。首次初始化可 seed，后续发布默认不 seed。
